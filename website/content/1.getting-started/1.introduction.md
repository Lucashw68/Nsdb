title: Introduction
description: Understand where NSDB fits between your Supabase schema and a Nuxt component.
---

NSDB is a Nuxt module that generates the repetitive client layer around your Supabase tables. It turns database types and PostgreSQL metadata into typed model handles, optional Pinia stores, and generic Vue components.

```text
Supabase table
  → Row / Insert / Update types
  → generated schema and relations
  → typed NSDB model
  → optional Pinia store
  → Vue component
```

Your component stays small:

```ts
const exampleTable = useExampleTable()

await exampleTable.fetch()
await exampleTable.create({ title: 'My entry' })
```

## What remains authoritative

- Supabase is the source of truth for schema and data.
- Supabase Auth owns authentication.
- PostgreSQL Row Level Security owns authorization.
- Supabase Storage owns files and bucket policies.
- Pinia is optional and enabled per model handle with `{ store: true }`.

::callout{type="warning" title="Security boundary"}
RLS remains the security boundary. NSDB metadata can reduce accidental client exposure, but it cannot authorize a database request.
::

## What NSDB is not

NSDB is not an authentication system, an ORM that replaces Supabase, a replacement for RLS, a design system, or an offline-first sync engine. Direct access through `useSupabaseApi()` and Supabase JS remains available when the generated model is not the right level.

## The design goal

The common path should read like application code, not infrastructure code:

```ts
const exampleTable = useExampleTable({ store: true })

await exampleTable.fetch()
const entry = await exampleTable.create({ title: 'First entry' })

await exampleTable.update(entry, { title: 'Updated entry' })
await exampleTable.remove(entry)
```

Async model operations reject on failure, so normal `try/catch` works. Reactive `error` state also exposes the latest relevant failure.
