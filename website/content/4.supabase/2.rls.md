title: Row Level Security
description: Treat PostgreSQL RLS as the authorization boundary for every NSDB request.
---

> RLS remains the security boundary.

NSDB calls Supabase from the client. Generated metadata and components cannot authorize those requests; only server-side policies can.

## Client metadata is defense in depth

| Setting | Client-side role |
| --- | --- |
| `selectable` | Allows a column in generated default selects. |
| `editable` | Allows a column in generated mutation shapes and forms. |
| `hidden` | Removes a column from generic UI. |
| `serverOnly` | Removes a column from client-generated artifacts. |

These options reduce accidental disclosure and invalid UI. A user can still call Supabase JS directly, so policies must reject unauthorized reads and writes.

## Minimum policy scenarios

Test that:

1. anonymous protected reads and writes fail;
2. user A can access user A rows;
3. user A cannot read or mutate user B rows;
4. user B sees no user A data after an identity transition;
5. Storage policies enforce equivalent ownership.

Prefer database defaults or triggers for owner IDs instead of trusting a client-provided value.
