This guide is for coding agents working in an application that consumes NSDB. It does not describe NSDB package internals.

Package files under `node_modules` are not reliable project instructions. Put the relevant guidance in the consumer repository, where the agent actually works. `AGENTS.md` is supported by Codex and Cursor. Claude Code uses `CLAUDE.md`; it can import a shared `AGENTS.md` with `@AGENTS.md`.

Do not replace an existing instruction file. Merge the short NSDB section below with the project's own architecture, commands, and security rules.

## Consumer guidance

```md [AGENTS.md]
## NSDB

- Prefer a generated `useXxx()` model when one exists. Use the lower-level APIs only for operations the generated model does not express.
- Direct mode, `useXxx()`, creates independent network-backed state. Store mode, `useXxx({ store: true })`, uses shared Pinia-backed state and cache behavior.
- The stable model operations are `fetch`, `refresh`, `invalidate`, `getById`, `createDraft`, `create`, `update`, `remove`, `subscribe`, and `unsubscribe`.
- Pass an existing generated Row directly to `update(row, changes)` or `remove(row)`. Do not assume the primary key is named `id` or re-extract it unnecessarily.
- Do not hand-edit generated models, schemas, stores, composables, enums, or database types. Change the NSDB configuration or database source, then regenerate.
- Treat PostgreSQL RLS and Supabase Storage policies as the authorization boundaries. `hidden`, `serverOnly`, `editable`, and `selectable` are client exposure metadata, not server security.
- Use `@nuxtjs/supabase` for authentication. NSDB does not replace Supabase Auth.
- Use `useSupabaseApiStorage()` for Storage operations. Do not assume that a Storage operation and a PostgreSQL mutation form one atomic transaction.
- Use generated relation aliases with `fetch({ include: [...] })` before building client-side joins manually.
- Generated model operations reject on Supabase errors. Do not interpret an empty result as an error. Lower-level APIs may return their documented discriminated response objects.
- In store mode, `fetch()` may reuse a fresh exact-query snapshot, `refresh()` contacts Supabase, and `invalidate()` marks cached snapshots stale without fetching.
- Realtime is opt-in. Call `subscribe()` and later `unsubscribe()`; a store is not synchronized with external changes merely because store mode is enabled.
- Persistent read cache is not offline-first mutation support. Do not invent an offline write queue.

Official documentation:
- Overview: https://lucashw68.github.io/Nsdb/
- Public API: https://lucashw68.github.io/Nsdb/docs/reference/public-api
- CRUD: https://lucashw68.github.io/Nsdb/docs/core/crud
- Direct vs Store: https://lucashw68.github.io/Nsdb/docs/core/direct-vs-store
- Cache and freshness: https://lucashw68.github.io/Nsdb/docs/core/cache-and-freshness
- Realtime: https://lucashw68.github.io/Nsdb/docs/core/realtime
- Relations: https://lucashw68.github.io/Nsdb/docs/supabase/relations
- RLS: https://lucashw68.github.io/Nsdb/docs/supabase/rls
- Storage: https://lucashw68.github.io/Nsdb/docs/supabase/storage
```

## Choosing an instruction file

- For Codex or Cursor, merge the section into the consumer's root `AGENTS.md`.
- For Claude Code, use a root `CLAUDE.md`. If the project already maintains `AGENTS.md` as its source of truth, add `@AGENTS.md` to `CLAUDE.md` rather than copying the rules.
- Keep existing project instructions authoritative. NSDB guidance should add package-specific constraints, not replace repository conventions.

::callout{type="note" title="CLI behavior in NSDB 1.0"}
`nsdb init` does not create or modify agent instruction files in NSDB 1.0. Automatic, overwrite-safe installation of this section is deferred so the stable CLI behavior remains identical to the validated release candidate.
::
